Fallout: New Vegas in your browser

This page runs Fallout: New Vegas from your own copy of the game: the game's program is recompiled to WebAssembly and drawn with WebGPU. It contains no game files, so you link the folder of your installed copy and the browser reads it from your computer. Read how to play for the steps, or about the project for how it works.

How this was made

Fallout: New Vegas came out in 2010 as a Windows program. This page runs that same program inside a browser tab. Nobody rewrote the game: its original code was translated, function by function, into a form the browser understands. Here is how, step by step.

1. The problem: browsers can't run .exe files

When you install the game you get FalloutNV.exe. Inside it is machine code: millions of tiny instructions for an Intel-style (x86) processor, such as "load the number at this address", "add these two numbers" or "jump to that function". The program also expects Windows to be there, asking it to open files, make windows and threads, and draw pictures through Microsoft's Direct3D 9 graphics system.

A browser offers none of that. It runs JavaScript and WebAssembly (a compact, fast code format that every modern browser can run), and it draws graphics through WebGPU. To get the game into a browser you have to bridge both gaps: the processor and the operating system.

2. Three ways to do it, and the one chosen

  • Emulate the processor: a program reads each x86 instruction while the game runs and acts it out. That works, but interpreting every instruction live is far too slow for a 3D game in a browser.
  • Rewrite the game by hand. That would take years, and the result would no longer be the original game.
  • Recompile it ahead of time: translate the whole program once, before anyone plays, into code the browser runs at near full speed. This is what this project does. Think of translating a whole book once, rather than hiring an interpreter to translate it aloud every time someone reads it.

3. Reading the machine code

A tool written for this project opens the exe and uses a disassembler (a library that turns raw bytes back into readable instructions like mov eax, [ecx+8]). It follows every call and jump to find where each function starts and ends.

A community project, fnv_decomp, helped enormously. Its contributors have worked out what thousands of the game's functions do and given them real names, so instead of "the function at address 0x004624B0" you can read what it is for. That made it possible to understand and debug the translated game.

4. Translating each function ("lifting")

Each machine-code function is rewritten as a C++ function that does the same thing. The processor itself becomes a small data structure: its eight general registers (eax, ebx, ecx…), its status flags and its floating-point registers. Every instruction becomes a line of C++ that updates that structure or the game's memory. For example:

; original x86 machine code         // translated C++
mov  eax, [ecx+8]                    s.eax = M32(s.ecx + 8);
add  eax, 1                          s.eax = s.eax + 1;   // plus the flags
call 0x004624B0                      f_004624b0(s);

Two tricks keep it faithful. First, the game's memory is laid out at the same addresses it had on Windows, so every pointer the game stores still points at the right thing. Second, when the game calls a function through a pointer (as C++ objects do for "virtual" functions), a lookup table maps the original address to the translated function.

5. Compiling to WebAssembly

The translated C++ is compiled with Emscripten, a compiler that outputs WebAssembly instead of a normal program. The result is about 95 MB of WebAssembly (around 14 MB compressed for download). Because the compiler optimises it, the browser runs the game's logic far faster than an emulator could.

6. Pretending to be Windows

The game still thinks it is on Windows, so the project includes a platform layer: stand-ins for the Windows functions the game calls. When the game asks Windows to open a file, the stand-in reads it from the game folder you linked. When it starts a thread, the stand-in starts a web worker (the browser's version of a thread), and the workers share one block of memory, as the game's threads expect. Keyboard, mouse and gamepad input are fed in as if they came from Windows, and the game's sound goes to the browser's audio system.

7. Turning Direct3D 9 into WebGPU

When the game draws a frame it makes Direct3D 9 calls: "use this texture", "use this shader", "draw these triangles". The stand-in for Direct3D writes those requests into a queue in memory, and a renderer written in JavaScript reads the queue and draws the same things with WebGPU.

The game's shaders (small programs that run on the graphics card and decide each pixel's colour) were written for Direct3D 9 too. Each one was translated, using open-source shader compilers, into WGSL, the WebGPU shader language: about 1,800 of them.

8. Your game files

The translated program is the engine: the code that runs the game. Everything you see and hear (the Mojave, characters, quests, textures, music and voices) lives in the game's data files. That is why you link the folder of your own copy: the browser reads those files straight from your computer, the same way the original game reads them from your disk.

9. The hard parts

  • Old floating-point maths. The 2010-era processor instructions for decimals (x87) work differently from modern ones and had to be imitated closely, or physics and animation go wrong.
  • Speed. Translated code is only fast if the compiler can tidy it up. The translator keeps registers in local variables and lets the compiler remove work whose result is never used.
  • Smooth frames. The game, the graphics card and the screen each run on their own clock. The page paces them so each screen refresh gets one finished frame, and an automatic quality setting shortens the view distance when your computer falls behind.
  • Finding bugs. When something breaks, it breaks inside translated code. Matching addresses back to the community's named functions is how most problems were tracked down.
